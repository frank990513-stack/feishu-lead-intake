# 接入指南

先用独立飞书测试表和包内虚构样例跑通，再用自己控制的表单发起测试询盘，验证来源端实际送出的字段。平台后台入口与按钮路径见[来源端设置](source-setup.md)；这里说明接收、解析、入表和回查。

## 百度爱番番推送

1. 在用户选定的云函数或 HTTPS 接收服务上部署接收逻辑。先让爱番番的后台测试从来源端实际发起一次请求，并在接收端确认到达。用同一端点分别核对鉴权和字段映射。阿里云函数计算可作为接收端，接收地址按实际环境配置。
2. 按爱番番当前配置核对线索编号、联系方式、摘要与完整会话的字段。示例采用 `clueId`、`emailAccount`、`additionalContent` 和 `formDetail`。示例的 `formDetail` 是 HTML 字符串。实际收到分段消息或嵌套结构时，按样例明确消息顺序和文本字段，再转成纯文本。保留有意义的换行，避免把整段会话塞进摘要。
3. 为每个已验证来源配置稳定的账号或站点别名。用平台支持的认证机制校验来源，再映射到别名。后台测试可能交付原样变量，如 `${clueId}`。记为连通测试，暂停入表，再用自有表单提交虚构询盘，检查变量是否真正替换。
4. 两个站点共用接收端时，各发一条测试线索，检查来源标签。如果能构造同编号的测试件，需确认互不覆盖。

## 官网表单通知经 Gmail 入表

1. 使用用户授权的 Gmail 账号读取指定的官网表单通知。按已知发件人、主题和表单结构缩小范围。渠道标签来自已核实的站点或表单映射。只有确认广告归因时才标为 Google Ads。
2. 调用 Gmail API 时，用 `messages.list` 枚举消息和分页，再按返回的 `id` 用 `messages.get` 取详情。读取正文可使用 Gmail 只读范围。按实际 MIME 结构解码正文，优先 `text/plain`，必要时将 HTML 转为纯文本。使用 Gmail API 返回的消息 `id` 去重，避免用邮件主题、发件人或 thread ID 把多封询盘误合并。 [Google 列出邮件](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) · [Google 获取邮件](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get)
3. 按通知模板映射字段。本文示例用 `Email`、`Product`、`Inquiry`。随包脚本只演练固定样例。为实际通知编写解析时，按表单结构判定字段边界，让解析覆盖字段分行和同一行两种格式，保留留言中的数量、标点和正文。用一条正文含 `Product:` 字样的询盘测试，确保留言里的字样不会被当作下一列。原始消息 ID 缺失、字段边界无法判定或有正文却提取不出留言时，保留待查状态和可用的来源标识。重新处理同一条时沿用原消息 ID。
4. 翻页或轮询时保留未确认入表的记录，让下一次能继续。只读账号使用独立的处理状态，按去重键回查飞书后再确认。若另行获准使用 Gmail 标签，再在回查完成后标记邮件。

## 写入飞书多维表格

1. 用 CSV 导入建立测试表，或手动创建同名文本列。核对导入后的列类型，并记录实际列名或连接器使用的字段标识。给连接器或应用开通目标表所需的查询、写入和文档访问权限。
2. 对去重键做完整值匹配。遇到分页，读完匹配结果再判断。零条才允许新增，一条回查字段，多条记录为冲突并暂停。对同一张表串行处理查重和新增。如果存在多个写入实例，共享一套串行队列，或用持久化唯一键协调。单独执行「先查再写」无法阻止两个客户端同时新增。
3. 使用飞书新增记录 API 时，将字段映射放在 `fields` 对象中。对同一次尚未确认的新增操作，持久保存并复用同一个 UUID v4 `client_token`。写入超时、回执不完整或令牌冲突时先查同一去重键，识别结果后再决定是否重试。避免为同一未知操作直接换新令牌重新新增。 [飞书新增记录](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create)
4. 记录每次测试的来源、用例、阶段、实际行数和核对结果。现场截图或回执分享前去除账号标识、目标地址、联系方式和原始业务内容。
